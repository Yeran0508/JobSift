JobSift 从零学习笔记
=====================

学习方式
--------
每节按“概念 -> 亲手创建或修改文件 -> 运行验证 -> 总结 -> 中英文面试问答”进行。
这份笔记只记录已经实现并验证过的内容。requirements.md 可以描述 V1 目标，但未接入、未测试或未测量的能力不会写成已完成。

项目目标
--------
JobSift 是面向软件工程求职的公开岗位聚合与搜索平台。完整 V1 将实现合规采集、Pandas 清洗、spaCy 实体与技能提取、
Elasticsearch 全文检索和筛选、搜索 API、用户界面、评测与可复现面试演示。

项目用途
--------
这是一个以软件工程简历和技术面试为核心的项目。每项核心能力必须同时具备代码、自动化测试、真实验证、限制说明和
简洁的中英文面试解释。没有实验报告支持的规模、准确率、完整率和延迟数字不能写进 README 或简历。

合规与实验纪律
----------------
1. 只采集 robots.txt 和网站条款允许访问的公开岗位信息；有公开 API 或数据源时优先使用，不绕过登录、验证码和限流。
2. CI 使用合成 HTML fixture，不依赖外部网站，也不把真实网站改版误判成项目代码回归。
3. 原始数据不可变保存，清洗结果记录转换规则；不能为了让展示好看而静默补齐未知字段。
4. 每次实验记录 Git 版本、数据版本与来源、参数、环境、步骤、基线、原始结果、限制和结论。
5. 目标不是结果。未真实测量的抓取量、搜索质量和 P95 延迟不能对外宣称。

第 1 节：M0 工程基线
--------------------

为什么先做 M0？
JobSift 后续会同时使用浏览器自动化、数据清洗、NLP 和搜索引擎。先固定语言版本、配置边界、测试、容器和 CI，后续出现
问题时才能区分业务逻辑、依赖、外部站点和环境差异。M0 只证明应用骨架可重复运行，不证明抓取或搜索已经实现。

本节创建的边界
--------------
1. Python 3.12 与 FastAPI：Python 适合 Selenium、Pandas、spaCy 和 Elasticsearch 客户端生态；FastAPI 提供类型化 API
   和自动 OpenAPI，便于把数据管线能力变成可演示的服务。
2. Settings：配置使用 JOBSIFT_ 前缀从环境变量读取。.env.example 只保存非敏感示例，真实 .env 被 Git 忽略。
3. Liveness：GET /api/v1/health 只证明进程和 HTTP 路由可用，不证明 Elasticsearch 或采集器 ready。
4. Docker：runtime 镜像使用非 root 用户；test 镜像追加 Ruff、pytest 和 coverage，开发工具缓存写入 /tmp。
5. 质量门禁：Ruff 检查常见错误和 import 顺序；pytest 验证健康接口与 OpenAPI；覆盖率门槛为 90%；CI 还验证 Compose。
6. Elasticsearch 边界：Compose 已声明单节点 Elasticsearch，方便 M3 接入，但当前应用没有索引或查询代码，不能说搜索已完成。

本节具体实施过程
----------------
第一步：克隆并确认空仓库。
从 GitHub 克隆 JobSift 后，用 `git status --short --branch` 和 `git remote -v` 确认当前是尚无提交的 main 分支，
远程地址指向 Yeran0508/JobSift。工作区中没有仓库级 AGENTS.md，因此按现有项目的学习方式建立全新工程。

第二步：先写 V1 边界和证据规则。
在写业务代码前创建 requirements.md，把完整 V1 拆成 M0-M5，并明确合规采集、不可收集的个人信息、CI 使用合成 fixture、
以及所有简历数字必须有可复现实验。README 只描述当前真实能力；docs/experiments/README.md 固定后续实验必须记录的字段。

第三步：创建 Python 工程配置。
pyproject.toml 固定 Python 3.12，声明 FastAPI、Pydantic Settings 和 Uvicorn 运行依赖，以及 pytest、coverage、HTTPX 和
Ruff 开发依赖。setuptools 从 backend 目录发现 jobsift 包；pytest 测试目录、Ruff 规则和 90% coverage 门槛也统一写在
同一文件中，避免本地与 CI 使用不同参数。

第四步：建立最小 FastAPI 纵向切片。
创建 config.py，把 JOBSIFT_ 前缀的环境变量解析成有类型的 Settings；创建 main.py 和 health.py，实现
GET /api/v1/health，并让 FastAPI 自动生成 OpenAPI。健康接口只返回服务状态、名称和版本，不主动连接 Elasticsearch，
因此它明确属于 liveness，而不是 readiness。

第五步：建立安全配置与容器边界。
.gitignore 排除真实 .env、缓存、构建产物和本地原始/处理数据；.env.example 只提供非敏感变量名。Dockerfile 分成
runtime 和 test 两个阶段：runtime 安装应用后切换到非 root 用户，test 只追加质量工具，并把工具缓存写到 /tmp。
.dockerignore 阻止 Git 历史、密钥、本地数据和学习笔记进入镜像上下文。

第六步：定义可重复的本地服务。
compose.yaml 定义 API、test 任务和 search profile 下的单节点 Elasticsearch。M0 默认只需要 API；Elasticsearch 虽然已
声明，但应用尚未使用。API 宿主端口通过 JOBSIFT_API_PORT 配置，容器内部固定为 8000，便于端口冲突时只改外部映射。

第七步：建立测试、接口文档和远程 CI。
健康测试验证精确 JSON 和 OpenAPI 中的路径；配置测试验证默认值与 JOBSIFT_ 环境变量覆盖。docs/api-contract.md 只记录
已经存在的 health API。GitHub Actions 在 Python 3.12 中安装项目，依次运行 Ruff、pytest/coverage 和 Compose 配置检查，
权限只授予 contents: read。

第八步：执行第一次门禁并修复真实失败。
第一次 Docker 化 Ruff 发现 import 分组问题；按固定版本 Ruff 的差异修复。第一次 pytest 虽然两个接口测试通过，但
Settings 未覆盖导致总覆盖率只有 61%；补充两个配置测试后，4 个测试全部通过且覆盖率为 100%。整个过程没有关闭规则、
降低门槛或排除业务模块。

第九步：完成真实 HTTP 验证和资源清理。
Compose 首次启动时发现宿主 8000 已被占用。保留未知进程不动，把同一 jobsift-api 镜像临时映射到 18080；容器内部和
宿主机请求都返回相同 health JSON。验证后停止临时容器，并用 `docker compose down` 清理本次创建的容器和网络，不删除
任何数据卷。

第十步：准备首次版本提交。
最终再次运行 Compose 配置解析、Python compileall 和尾随空白扫描，并检查待提交文件清单。首次提交包含 M0 代码、测试、
文档、CI 和学习笔记；推送后再用远程 main 的 commit SHA 判断 GitHub 是否收到完全相同的版本。

运行验证
--------
1. `docker compose config --quiet`：通过，Compose 配置能够完整解析。
2. Python 3.12.10 test 镜像：成功构建；运行用户为非 root，Ruff 和 coverage 缓存写入 /tmp。
3. `ruff check .`：All checks passed。
4. pytest：4 个测试通过，0 failures；应用代码覆盖率 100%，高于 90% 门槛。
5. HTTP：容器内部的 8000 端口和宿主临时 18080 端口都返回
   `{\"status\":\"ok\",\"service\":\"JobSift API\",\"version\":\"0.1.0\"}`。
6. 尾随空白扫描和 Python compileall：通过。

本节实际遇到的问题与排查
--------------------------
第一次 Ruff 检查报告两个 import 分组问题。测试镜像中的项目已作为 jobsift 包安装，因此 Ruff 把测试里的 jobsift import
和其他已安装包放在同一组；按固定版本 Ruff 给出的差异调整后通过。没有关闭 I001 规则掩盖问题。

第一次 pytest 的两个 health 测试都通过，但覆盖率只有 61%。未覆盖部分是 Settings 和 get_settings。新增默认值与
JOBSIFT_ 环境变量测试后共 4 个测试通过，覆盖率达到 100%；没有降低 90% 门槛或排除配置模块。

第一次用 Compose 启动 API 时宿主 8000 端口已被其他进程占用，镜像构建本身成功。没有停止未知进程，而是把同一镜像
临时映射到 18080，并分别从容器内部和宿主机验证健康接口。随后停止临时容器，并把 Compose 宿主端口改为可通过
JOBSIFT_API_PORT 配置，默认仍是 8000。

测试出现一条 Starlette TestClient 内部 AnyIO alias 的弃用警告。它不是 JobSift 直接调用的 API，当前不影响结果；后续
升级 FastAPI/Starlette 时需要重新检查，不能通过全局隐藏 warning 把它当作已解决。

本次运行总结
------------
M0 已在本地完成并通过真实验证：固定 Python 3.12 镜像可构建，配置边界、liveness、OpenAPI、Ruff、pytest、覆盖率和
Compose 配置均可重复验证。首次提交推送后，远程 CI 是否通过仍以该 commit 对应的 GitHub Actions 结果为准，不能用

Selenium、Pandas、spaCy 和 Elasticsearch 业务接入均未开始，也没有被写成已实现。

简约面试回答
------------
问：为什么 JobSift 使用 Python 和 FastAPI？
English: Why did you choose Python and FastAPI for JobSift?
中文：核心数据链路依赖 Selenium、Pandas、spaCy 和 Elasticsearch 的 Python 生态。FastAPI 提供类型校验和 OpenAPI，
可以用较小的服务边界暴露搜索能力。EVFinder 已经展示 Java/Spring Boot，因此这里选择 Python 也扩大了技术覆盖面。
English: The core pipeline relies on the Python ecosystem around Selenium, Pandas, spaCy, and Elasticsearch. FastAPI
adds typed validation and OpenAPI with a small service boundary. EVFinder already demonstrates Java and Spring Boot,
so Python broadens the backend stack shown by the portfolio.

问：为什么 health check 不能证明搜索功能可用？
English: Why does the health check not prove that search is available?
中文：当前 health 是 liveness，只验证 FastAPI 进程和路由。搜索还依赖 Elasticsearch、正确 mapping 和已完成的索引；
这些条件应在 M3 用单独的 readiness 与真实集成测试验证。
English: The current endpoint is a liveness check for the FastAPI process and routing. Search additionally requires a
healthy Elasticsearch cluster, the expected mapping, and a completed index, which M3 will verify through readiness and
real integration tests.
